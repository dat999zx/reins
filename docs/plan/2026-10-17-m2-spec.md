## 0. Real-CLI facts [probe]

- P1: three sessions in one folder at once are independent (own approval callback, own totals, no rate-limit errors, wall time 1.2x one session). Not tested above 3.
- P2: interrupting a turn mid-reply returns it with empty text and NO total (its spend is not counted); closing a session mid-turn rejects its turn with Error "closed".
- P3: the per-process cap (`--max-budget-usd`) is checked between model calls: with cap 0.002 the turn stopped after its first call, which cost 0.0048. A process overshoots its cap by at most one model call, and one call can cost more than the whole cap.
- P4: the cap counts from the process start, not from the session's total. So a cap passes `share - spent`, never `total + share`. Not exercised: crossing the cap on a resumed session.
- P5: two sessions appending to one file at once both land; the CLI's stale-read check makes the second re-read. Same-line edits, big files, more than 2 writers: not tested.
- P7: interrupting a turn while a tool approval is pending (the host's `onApprove` promise never settled) ends the turn in about 84 ms: not an error, empty text, its total counted (0.0076); the interrupt call resolves in 84 ms; the tool did not run. So the ENGINE side of a stop with a pending approval does not hang. The hang risk is the HOST side: a question promise (judge, gate, trust, tool) that nobody settles while `close()` awaits a track. The pending `onApprove` promise must still be settled on stop, so nothing leaks.
- Engine quirk: `OpenOptions.sessionId` set means `--resume`; a new session is opened without it and its id read from the session.

## 1. Goal

A workflow can split into branches that run at the same time, and can run another workflow as one block.

- **`fork`**: a block in the stack. Drag as many wires out of it as you like; each wire starts a branch (a chain of free blocks behind the `end`). All branches run at once, each in its own conversation. When every branch has finished, the run goes on with the block under the fork, which gets each branch's last reply, quoted as data.
- **`playbook`**: a block that runs another workflow file with inputs and outputs, either in the same conversation (inline, compiled in) or with `session: own` in a conversation of its own, with an optional USD budget. It is the only way to reuse a file: `use` is removed (5.5).

Both are written ONLY as M1 blocks: `nodes/fork.ts` + `nodes/fork.view.ts`, `nodes/playbook.ts` + `nodes/playbook.view.ts`, one import and one list entry each in `nodes/index.ts`. Fork's rule F11 also adds a `validate.program` rule to `nodes/verify.ts`, so fork touches three node files. Whatever the engine needs beyond the M1 contract is added to the contract (section 3), named for what it does, never for a kind.

## 2. Non-goals and known limits (M2)

Non-goals:
- Steering one branch, stopping one branch only, a fork inside a branch or inside a playbook (nested fork), live streamed branch text in the feed.
- File isolation per branch (worktrees). Branches share the folder (decided).
- A `maxParallel` cap. More than 3 branches is unmeasured (P1). A cap is not a one-line hook (setting, server read, UI field); `vm.tracks.start` is where a later cap goes.
- Per-branch `usd:` on plain blocks.
- `against:` from the calling workflow to a step inside a playbook (verify checks `against` against parsed ids, `nodes/verify.ts:53-57`). Inside the playbook, `against:` works (5.2).
- A migration of old `## use` lines: none (the user's decision; the error says what to write instead).
- M3 (plugin loading, sharing) and M4 (the rename). Section 9 lists what M2 leaves open for M3.
- Fixing the pinned M1 baseline bugs (section 8), except the canvas chips item the orchestrator scheduled (plan Task 19). The `use` collision item is moot: `use` is removed (plan Task 20) and playbook ids cannot collide (5.2).

Known limits (said in the changelog or the open questions):
- With no workflow USD budget, branches and own playbooks have no cap except their own `usd:` or an open slice.
- A reply cut off by Stop may not be counted: P2 (mid-reply) reports no total; P7 (waiting for an approval) does.
- In the terminal (`reins run`), a branch's tool approvals are not titled, and branch text prints interleaved without a label: the terminal's one engine has one `onApprove` (`run-cli.ts:128`) and one `onLive` (`printLive`, `:165-171`). Pause cards (gate, resume, budget) are titled in the terminal too. Titled tool approvals are server-only in M2.
- `attempts` conditions sum every loop counter of the run (`conds/attempts.ts:30`, `loopTotal`, `run.ts:776`), branches included.
- A `whenever` card is checked only after turns on the main session.

### 3.4 Tracks and `VmCtx`

A **track** is one program counter with its own pause, in-flight turn, held interrupt card, last reply, last step id, policy, recall context, handback, waiting notes, open USD slice, own session and its money record. The **main line** is track `''`. Every other track has its OWN session (inline playbooks are compiled in and are not tracks, 5.3), a **parent** (the track whose op started it) and a **group** (that op's step id).

```ts
export interface TrackSpec {
  /** Unique among live tracks: a branch uses its first step id, an own playbook its step id. */
  key: string;
  at: number;
  /** Card and receipt title, e.g. "Branch API research", "Playbook review-pass". */
  title: string;
  /** Texts its first turn carries (the caller quotes them). */
  seed?: string[];
  /** A USD slice of its own (playbook `usd:`). */
  usd?: number;
  /** Shares the room equally with the other tracks of the same start() call (4.6). */
  share?: true;
}
export interface TrackResult { key: string; title: string; text: string; cost: number }

export interface VmCtx {
  // ...M1 members, each now the track's own (table below)...
  readonly tracks: {
    /** Starts the tracks in order and parks this track on its instruction until every one ended; then this op runs again. Throws when `group` is live. */
    start(group: string, list: TrackSpec[]): void;
    /** Once every track of `group` ended: their results in start order, and the group is forgotten. Undefined when never started. */
    take(group: string): TrackResult[] | undefined;
  };
  /** The next turn of this track carries `text` (the caller quotes it). */
  handBack(text: string): void;
  /** This track's last reply, read live. */
  lastReply(): string | undefined;
}
```

Scheduler, in `Run.step()`:
1. No live track other than the main line: today's body on the main line, unchanged (the single-track path).
2. Otherwise: start the next instruction of every runnable track that has none in flight, then return when the first settles or the run changes (an answer, a stop: `changed()`, 3.6). Runnable = its status is running, it is not parked, and the run is not paused.
3. A track ends at `END` or past the program end (main line keeps `run.ts:947-951`, `:1049-1053`). Its **result** is its last reply without `REINS:` lines (the rule of `run.ts:538`), then any handback entry it never passed on. It closes its session, sets `ended`, then logs `track_ended`.
4. When the last track of a group ends, the parent is runnable; its counter is still on the op, so the op runs again and calls `take`.
5. A throw from a non-main track's instruction pauses that track (words in the plan table), unless the run is stopped or **closing** (S7: a `close()` that is not after a Stop, such as a detach, rejects in-flight turns with "closed"; those tracks stay `running` so they run again on restore). A throw on the main line still reaches the driver (`drive.ts:68-71`).

Per-track rules that keep the main line as it is:
- **Money record (S2).** An own track's turns write their cost and totals into the track's record (like `SubagentRecord`, `run.ts:112-118`), never into `lastTotal`/`lastTotals` (`run.ts:649-650`), which open the main session (`:308`).
- **Cards (S3, S4).** Cards (`queueCard`, `run.ts:345-365`) reach only the main session. TURN drains `pendingCards` (`:984-985`) only on the main line. A resumed subagent takes `pendingCards` (`:517`) only on the main line; on another track it takes that track's notes. A `now` card typed during a fork waits in `pendingCards` (snapshotted) and lands under the fork.
- **Stop card.** While tracks run, a stop card is one run-wide stop pause: one `run_paused`; every in-flight track turn is interrupted and marked so its step runs again on Resume (never taken as a reply).
- **Conditions (S8).** `evalCtx(t)` gives a track only the command results it recorded (`CommandResult.track`, absent on the main line) and only the events it logged (`data.track`). So two branches each in `repeat until tests pass` read their own runs (`conds/tests.ts:20`, `cmd.ts:32`, `same.ts:17-20`). `drift` and `touches` read the track's events. `attempts` stays run-wide (known limit). The main line reads only untagged entries, which with no tracks is everything, as today.
- `Run.policy()` (`run.ts:292-294`, read by the main session's engine) stays the main line's policy; own sessions are opened with their track's policy closure.
- `checkAutoCards` (`:1005`) runs only after main-line turns.
- **Edit (S12).** With a live track other than the main line, `edit()` (`run.ts:795-822`) gives the run's `step-deleted` pause (the driver stops it, `drive.ts:139-142`). With none, it is today's code. (`edit()` has no caller in any host `src` today [the review's grep].)
- **Host capabilities.** `ExecCtx` (`run.ts:412-422`) for a non-main track has no `switchModel` and no `setReasoning` (they act on the main session). F10 refuses a `model` block in a branch and in an own playbook (4.3, 5.3).
- **Nesting (S9).** An own playbook inside a branch, or inside another own playbook, is a track whose parent is a track. Its cap comes from its own `usd` and its parent's share left (4.6); its spend counts toward its parent's spent. A fork may not run inside any track (F9).

### 3.6 Run API and the `driveRun` state machine (S5, S6, B1)

`driveRun` (`drive.ts:52-78`), written once:

```
loop until detached:
  for each track pause in run.pauses() (p.track set) not yet being asked:
      start onPause(run, io, p) without awaiting it; when it settles, forget it; a null answer means detached
  if run.status is 'stopped' or 'done':      -> settle every open question of this run (io.cancel), break
  if run.status is 'running':                -> await run.step(); save(); setImmediate
  else ('paused'):
      if the run's OWN pause is open (no p.track) -> await onPause(run, io, run's own pause)   (today's path, byte for byte)
      else                                       -> await the first of: the open asks, run.changed()
finally: io.cancel (every question of this run is settled: tool, judge, trust, other tracks' gates);

```

- Track pauses are asked ONLY on the parallel path; `onPause` asks only the run's own pause, so no pause is asked twice.
- `DriveIo` gains `cancel(why: string): void`. Server: closes every pending question whose run id is this run's (`pending`, `session.ts:81`; `closeQuestions` per run). A closed tool question answers `deny`, so the engine's pending `onApprove` promise settles (P7: the engine side ends in about 84 ms on interrupt). Terminal: answers every waiting `asks` entry with `null` (`run-cli.ts:39-51`).
- `onPause` for a keyed `resume` answer calls `run.resume(p.track, note)` instead of queueing the note as a run-wide steer card (`drive.ts:133`).

### 4.4 Run time, step by step

Compile: `FORK { step, targets, keys }`, one entry per `next` link in wire order, via `ctx.linkTo`. Op: `next: (i, at) => [at + 1, ...i.targets]`, `starts: (i) => i.targets`.

1. The main line reaches FORK. `take(step)` is undefined, so FORK starts the branches: key = target step id; title = `Branch <title of the target step, else its id>`; `share: true`; seed = the quoted last reply before the fork, if any. `start` logs `track_started` per branch; FORK logs `fork_started`; the main line is parked on FORK.
2. Every branch runs at once in its own session (3.8). Its first turn carries the seed under "For this step:" (`compile.ts:85-97`). Inside a branch everything runs as on the main line.
3. A branch ends at an `end` or the program end, logging `track_ended`.
4. When every branch ended, FORK runs again: `take` gives the results in wire order; each goes to the main line's handback, quoted; FORK moves its counter; then logs `fork_done`.
5. In a `repeat`, each pass starts fresh branches (`take` forgot the group). Loop and link counters keyed by step id carry over passes, as nested loops do today.

Quotes (fork.ts's own helper): fenced with one backtick more than the longest backtick run (at least three), capped at the last 8,000 characters with the cut said. The subagent's fixed fence (`run.ts:187-188`) stays (changing it changes goldens B2, S8).

### 4.6 Money (P3, P4, B2, B3)

Today: run cost (`run.ts:233`), slices (`:235-237`), the check between steps (`:955`, `usdOver` `:556-574`), a subagent's cap from the smaller of its slice room and the workflow room, rounded up (`:477-501`), both computed from the one shared `usdSpent` (`:482`, `:488`, `:653`).

- **Room** at a `start` with `share: true`: `room = min(workflow room, open slice room)`, each when it exists (workflow: limit plus allowances minus run cost, unrounded as `:487`; slice: the slice open on the starting track, its usd plus allowance minus `usdSpent`). No room (neither exists): no shares, no caps except a track's own `usd`.
- **Shares (B2).** `share = room / N`, rounded UP to a **millionth of a dollar** (a micro-dollar), not to a cent. This is what M2 built and what its tests pin (`capOf` in `packages/core/src/run.ts`, the one cap rounding). Example: a `model` block with `usd: 0.50` before a fork of 3, no workflow budget: each share is 0.166667 (this spec first said 0.17). A workflow room of $1.00 over 3 branches is 0.333334 each. Rounding up lets the shares pass the room by under one millionth per branch; the run-wide check between steps still holds the limit.
  - Why a millionth: the plan v5.1 said a share is rounded "as a cap is rounded" (`run.ts:534` then), and that one rounding is up to a micro-dollar. A cap a hair under Reins' own limit would end a reply as an error that `usdOver` (tolerance 1e-9) does not see as reached, so the cap must never sit below the limit; the figure is first rounded to nano-dollars so float noise (0.2000000000000001) does not push it up a whole micro-dollar. The M2 Task 12 report (rounding, item 1) records that the "to a cent" of the earlier plan text lost to the v5.1 words. This is not a bug; do not change it to a cent without changing the tests that pin it.
  - Everywhere this spec and the plans say "rounded up to a cent" for a share or a cap (4.6 below, the B2 test of the plan, the bound), read "up to a millionth". The "free room of a cent or more" test below is a different number and stays a cent.
- **Every branch reply** adds to the run cost, to its track record (S2), and to the open slice it copied at start (the shared `usdSpent` entry), through `runTurn` (`:641-653`).
- **`shareFor(track)`**, one function: the next process's cap = `min(own usd room, share - spent)`, rounded up as `:499-501`. P4: `share - spent`, never `total + share`. A subagent or own playbook inside a branch: `min(its own room, its branch's share - the branch's spent)`; its spend counts toward the branch's spent.
- **A capped reply** (`isError` on a track whose spend reached its share) is not a reply: the instruction runs again, and its next turn sends `CARRY_ON` (`run.ts:183`) instead of the step text (S18), on the resumed session. Free room = room now minus what the other live branches still hold (each `max(0, share - spent)`). Free room of a cent or more: **`share := spent + free room` (B3)**; the session is dropped and reopened with `--resume` under the new cap; a `budget_warning` row says so; no card. Less than a cent: ONE run-wide `usd-budget-used` pause (today's card, `drive.ts:108-126`). Its "Allow $n" raises `usdExtra['']` (`run.ts:389-409`); every live branch then gets `share := spent + new room / live branches`.
- Worked numbers (Task 12 test 5): workflow $1.00; $0.10 spent before the fork; three branches at 0.30; A capped after spending 0.31; B holds 0.30 unspent; C ended at 0.05. Room now = 1.00 - (0.10 + 0.31 + 0.05) = 0.54; free = 0.54 - 0.30 = 0.24; A's share = 0.31 + 0.24 = 0.55; A's new cap = 0.24. Check: 0.10 + 0.55 + 0.05 + 0.30 = 1.00.
- **The bound (B3).** Each process start can overshoot its cap by one model call (P3), and a reopen starts a process whose first call re-reads the whole context. So the run's spend passes its limit (with allowances) by at most **one model call per branch, plus one per re-share**. The main line adds nothing while parked.
- The slice-sum error (`validate.ts:164-169`) is unchanged.
- Turn budget: counted over every session (`run.ts:479`); used up: one run-wide pause, the driver stops the run (`drive.ts:139-142`).

### 4.7 Stop and pause (P2, P7, B1)

| Case | What happens |
|---|---|
| Stop (button, Stop on any card) | `stop()`: the run is `stopped`; every in-flight turn on every session is interrupted and awaited. `driveRun` then settles every open question of the run (`io.cancel`, 3.6), so no track waits on a judge, gate, trust or tool question; then `close()` closes every track session first and only then awaits every in-flight track. An interrupted turn returns empty text; whether its spend is counted depends on where it stopped (P2: no total; P7: total counted). | Stop card | one run-wide stop pause (3.4); interrupted branches run their step again on Resume |

| A gate in a branch | its own card, titled; its text is the branch's last reply; "Request changes" goes to the branch's session |
| Workflow USD or an open slice used up | one card for all branches (4.6) |
| Detach (asker gone) with branches in flight | `close()` rejects their turns ("closed"); they stay `running` in the snapshot and run again on resume (3.4 rule 5) |

### 5.1 File format

- Heading argument: a file in the `blocks/` folder next to the workflow, through `resolveBlock` (`run-cli.ts:229-239`), which `use` used and playbook keeps (its name stays; M4's rename may change it). The heading owns `playbook` (the pattern of `nodes/use.ts:29-33`).

- `input:` one line of `name = value` pairs separated by `;` (a repeated attribute line overwrites, `parse.ts:172-174`). `output:` step ids of the file, separated by `,`. `session: own`, or absent for inline. `usd:` only with `session: own`.
- All print back in file order (`print.ts:103-109`).

### 5.2 Inputs, outputs, prefixing

- **Inputs** are filled in at compile time: every `{{name}}` in the playbook file's steps is replaced by its value: prompts, attribute values, card texts and **conditions** (`until:` strings, so a `command "npm test -- {{target}}"` condition gets the value). Conditions are included because trust reads them from the compiled instructions (`trust.ts:32-34`). Values are inserted as they are, with no quoting: the trust list is the guard, and it shows the filled-in commands. A `{{name}}` with no input is an error; an unused input is a warning.
- **Prefix (S11).** Inner step ids become `<step>/<id>` (the playbook's step id, not the file name `use` used, `use.ts:8-24`). The prefix rewrites `links` AND `attrs.against` when it names an inner step, so an inner `verify against: findings` reads `<step>/findings` (`verify.ts:12`). Playbook has its own prefix helper (written fresh; `use.ts` is deleted in plan Task 20).
- **Ids never collide.** Step ids of the calling file are unique (`validate.ts:78-88`), and inner ids carry the playbook step's id, so two playbooks of one file get `playbook-1/review` and `playbook-2/review`. One case is left: a calling step whose id already contains `/` (for example `id: playbook-1/review`). A generic check catches it: in the clean-program stage, compile with `starts` (`compile.ts:113`, `:138`) and report any step id that starts at two indices (plan Task 14 test 6). It names no kind and costs a few lines, so it is kept even though `use` is gone.
- **Outputs**: a step's reply is stored under its id (`run.ts:1003`), so output `findings` is in `vm.outputs` under `<step>/findings`.
- After an own playbook ran, each declared output goes to the parent's next turn, quoted as data; with none declared, its last reply. An output step that never ran is handed as `<name> did not run`. An inline playbook hands nothing back: its replies are already in the same conversation (Q3). This default still reads right with inline as a compile step: nothing is "returned" from a compiled-in run.
- The playbook file's frontmatter and `whenever` cards are not used (as with `use` before). The file IS validated on its own (`ValidateCtx.checkBlock`, as `block: true`); its errors are reported on the playbook step with the file's line.

### 5.3 Run time: inline is compiled in; own is a track (S10)

**Inline** (no `session:`), a compile step (as `use` was), on the single-track path:

```
k:      PLAYBOOK { step, playbook, session: 'inline', after: m }      logs playbook_started, moves on
k+1..:  the file's steps, prefixed, inputs filled in; each inner END rewritten to JUMP m (through ctx.get(i))
m:      PLAYBOOK_END { step, playbook }                                logs playbook_done, moves on
```

An inner `end` ends only the playbook (`use`'s inner `end` ended the caller, `nodes/end.ts:7`; that comment is rewritten in Task 20). Gates and pauses inside it are the run's own. No track, no new session, cards reach it as any main-line step.

**Own** (`session: own`):

```
k:      PLAYBOOK { step, playbook, session: 'own', start: k+1, after: m+1, usd?, outputs }
k+1..m-1: the file's steps, prefixed, inputs filled in (inner END stays END: it ends the track)
m:      END
m+1:    the step under the playbook
```

Ops: PLAYBOOK `next` = inline `[at + 1]`, own `[i.start, i.after]`; own `starts: (i) => [i.start]`. Own PLAYBOOK calls `take(step)`: undefined, so it starts ONE track (key = its step id, title `Playbook <name>`, `usd`), logs `playbook_started`, returns parked. When the track ended it runs again: `take`, hand back (5.2), `vm.next()`, log `playbook_done`.

Validation (words in the plan table): not found; `session:` not `own`; `usd:` without `session: own`; malformed `input:`; a `{{name}}` with no input; an unused input (warning); an output that is no step of the file; a cycle; the file's own diagnostics; a step id that starts twice (5.2); a `model` block in an own playbook (F10's rule for playbooks; inline keeps `model` working, it is the main session). Nesting is bounded: compile adds nothing when the prefixed id has more than 8 `/` segments (ponytail).

Why compile it into the same program: trust, models, the reach walk, the snapshot and the receipt work with no new path (`trust.ts:25-48`, `validate.ts:263-288`). `edit()` during a playbook: its inner ids are not parsed ids, so `findStepById` (`run.ts:805`, `:927-940`) gives `step-deleted`, as it did for `use`; with an own playbook live, the 3.4 rule gives the same.

### 5.4 Trust and the command list

`commandsOf` and `modelsOf` (`trust.ts:25-48`) walk the compiled program, which holds every playbook's steps with inputs filled in (prompts, attributes, conditions). So the commands of every playbook are in the trusted list, and the hash (`trust.ts:50`) asks again when an input changes a command. `trust.ts` does not change.
